# 0013 — Calendar access moves from the claude.ai connector to a first-party Google Calendar client
**Context.** Calendar writes (ADR 0008) went through the claude.ai Google Calendar connector's own tools, loaded into the `claude -p` CLI from Matthew's claude.ai account. Those write tools kept dropping out / going unavailable, so "add X to my calendar" started failing with nothing in this repo to fix — the connector is on claude.ai's side, not JARVIS's. The undo/change-log mechanism also depended on sniffing the brain's tool-call stream for the connector's exact tool names and hoping a `get_event` call landed earlier in the same turn.
**Decision.** Give JARVIS its own Google Calendar OAuth client (refresh token in `.env`, like every other secret here) and its own tools — `list_events`, `create_event`, `update_event`, `delete_event`, `respond` (`src/tools/calendar.ts`, `src/googleCalendar.ts`) — exposed the same way `add_idea` is, not as a connector. Each write tool fetches its own "before" snapshot and calls `calendarLog.record()` directly; `undo_calendar_change` performs the reversal itself through the same client, rather than handing instructions to the brain. The background worker's calendar-range job (behind the Calendar window and Today digest, JD-21) is left on the connector for now — its reads were not the reported problem, and switching it is a separate, larger change.
**Consequences.** One more OAuth credential to set up and keep alive (a refresh token, obtained once via `npm run setup:calendar`) instead of relying on claude.ai's own connector session — but it's no longer something that can silently "drop out" on claude.ai's side. Undo is now deterministic instead of best-effort through the brain. The worker's calendar reads and the interactive brain's calendar access are on two different paths until a follow-up moves the worker too.
